### Решение по версии игры
Отдельная Gothic II Classic больше не продаётся (Steam/GOG — только Gold, отключить дополнение
официально нельзя; сообщество использует мод «Classic»). Пользователь нашёл раздачу на old-games.ru —
отказались: игра продаётся, а русская версия требует NoCD (обход защиты исключён планом, хэш EXE
не закрепить). У пользователя есть **купленная оригинальная Gold-копия**. Решили: цель — Gold с двумя
вариантами (Ночь Ворона и классика); для тестов пиратские копии не используются — вместо пересылки
2,6 ГБ пользователь присылает отчёт о сборке.

## 2026-10-14 — Winlator встроен в приложение

Пользователь отказался от ручной проверки в Winlator («сложно, всё делаешь ты»). План изменён:
среда исполнения встраивается в наше приложение, от пользователя — только установить APK, нажать
«Играть» и прислать журнал.

- Исходники Winlator 11.2 (`brunodev85/winlator-app`, LGPL-2.1) — модуль `:winlator`; скачивает
  `tools/fetch-winlator.sh`, наши правки — `third_party/winlator.patch`. В Winlator 11.2 есть D7VK
  (Direct3D 7 → Vulkan) — готовая вторая графическая цепочка для Gothic.
- Главная проблема: rootfs Winlator собран с путём `/data/data/com.winlator/files/rootfs` (интерпретатор
  ELF, `ld.so.cache` и ещё ~165 файлов). Решение — при распаковке заменять его строкой той же длины
  `/data/data/<наш пакет>//////r`. Тесты: `WinlatorIntegrationTest`.
- `targetSdk 28` (как у Winlator): иначе Android не даёт исполнять Wine из каталога данных.
- `GameActivity` — наследник `XServerDisplayActivity`; наш оверлей поверх; `XServerInputSink`
  переводит скан-коды DIK в коды X. Подготовка (установка Wine, контейнер, INI, вариант) —
  `GameLauncher` с прогрессом на экране запуска. Заглушка `StubRuntimeBackend` удалена.
- Вывод Wine/Box64 пишется в `files/logs/wine.log` и попадает в экспорт журнала диагностики.
- GD3D11 (`System/ddraw.dll`) прячется на время игры в обоих вариантах (`rename=`).
- Debug-подпись — общий ключ `app/debug.keystore`, чтобы обновления ставились поверх.
- APK со всеми файлами Wine весил 164 МБ, а передать пользователю можно не больше 30 МБ. Архивы
  `*.tzst` вынесены из APK: при первом «Играть» приложение скачивает их (≈100 МБ) с GitHub
  закреплённого коммита Winlator с проверкой SHA-256 (`RemoteAssets`). APK — 24 МБ.
- Сессия: автоклассификатор запрещал сборку стороннего кода; пользователь разрешил через
  `.claude/settings.json` (`./gradlew`, `tools/fetch-winlator.sh`).

### Ожидается от пользователя
Установить новый APK (24 МБ) поверх старого, нажать «Играть» при включённом интернете, дождаться

Если игра не запустилась или работает плохо — Настройки → «Экспорт журнала диагностики» и прислать файл.

### Первые запуски на телефоне (2026-10-14)
- Wine, X-сервер, шрифты и наш оверлей работают: игра показывает окна Union/GOG.
- При первом запуске GOG-сборка выводит «Первый запуск! … DEP был изменен … перезапустите игру»,
  затем Union — «Can not create Event object», и игра закрывается. Журнал пользователь прислать не смог
  (экспортированный файл оказался пустым).
- Исправлено: процессы Wine прошлой игры завершаются при выходе и перед новым запуском (Winlator
  делал это перезапуском приложения); сначала SIGTERM — wineserver сохраняет реестр (иначе настройки
  «первого запуска» терялись бы), через 3 с — SIGKILL. ESync выключен (`WINEESYNC=0`) — подозрение,
  что с ним Union не создаёт событие. Журнал Wine прошлого запуска сохраняется (`wine.1.log`);
  отправка журнала через «Поделиться»; после быстрого выхода из игры лаунчер показывает экран
  «Отправить журнал / Играть снова / Настройки» вместо автозапуска.
- С `WINEESYNC=0` ошибка Union ушла — подтверждено на телефоне. Следующая остановка — движок Gothic:
  «C: maximum texture size is lower than 32» — WineD3D через Gladio (OpenGL Winlator по умолчанию) не
  дал рабочего 3D-устройства Direct3D 7. Добавлен выбор режима графики (`GraphicsMode`: D7VK,
  WineD3D+Zink, WineD3D+Gladio), по умолчанию D7VK; на экране неудачного запуска — кнопка
  «Играть с графикой: <следующий режим>».
- **Gothic II запустилась на телефоне** (главное меню, загрузка мира) в режиме WineD3D + Zink; D7VK и
  WineD3D + Gladio дают «maximum texture size is lower than 32». Zink стал режимом по умолчанию.
  После вступительного ролика (классика) — вылет, причина пока неизвестна.
- Журнал диагностики был пустым всегда: `kotlin.io.path.appendText` не создаёт файл (APPEND без
  CREATE), ошибка глоталась `runCatching`. Исправлено (`Files.write(..., CREATE, APPEND)`), тест
  `DiagnosticsTest` в `app`.
- Журнал вылета после ролика (классика, WineD3D + Zink через Vortek): в нём нет строки о выходе игры —
  погиб весь процесс приложения, а не Wine. Vortek выполняет Vulkan игры в процессе приложения, поэтому
  подозрение на его нативный сбой или нехватку памяти. Добавлено:
  - `CrashRecorder`: необработанные исключения Java сразу пишутся в журнал, а при следующем запуске —
    причина гибели прошлого процесса из Android (`getHistoricalProcessExitReasons`: CRASH_NATIVE,
    LOW_MEMORY и т. п., память процесса);
  - режим «WineD3D + Zink (Turnip, Adreno)»: драйвер Vulkan Turnip в процессе игры, без Vortek; на Adreno
    он теперь по умолчанию (видеокарта запоминается при запуске), выбор игрока имеет приоритет;
  - после прерванного сеанса лаунчер показывает тот же экран, что после неудачного запуска (журнал,
    «Играть снова», «Играть с графикой: …»), с текущим режимом графики.
- **С режимом «WineD3D + Zink (Turnip)» игра работает и не вылетает** («Ночь Ворона», Adreno 740,
  10 минут игры). Жалоба — периодические фризы: в одних местах плавно, при повороте камеры (возможно,
  в сторону огня) — подвисания. В журнале Wine: «Forcing serialization of all command streams» — Winlator
  ставит WineD3D `csmt=3`, где бит 0x2 заставляет игру ждать выполнения каждой команды отрисовки.
  Теперь `csmt=1` (обычный отдельный поток отрисовки, как в Wine по умолчанию).
- Журнал раз в минуту пишет плавность картинки (`FrameStats`, строка `[frames]`): FPS, перцентили
  интервалов кадров, число фризов (>100 мс) и пауз (>1 с). По ним видно, помогли ли изменения и
  в чём причина: редкие длинные фризы при первом взгляде на эффект — компиляция шейдеров (кэш Mesa
  сохраняется, второй раз быстрее), стабильно низкий FPS у огня — нагрузка на процессор (динамический
  свет Gothic считается на CPU, а он эмулируется Box64).

### Фризы: разбор журнала, быстрые ядра, загрузка процессора в журнале (2026-10-14)
Журнал пользователя (классика, WineD3D + Zink (Turnip), Adreno 740): `csmt=1` применился; ошибок Wine,
связанных с плавностью, нет (`nsi`, `rpcss`, `libEGL.so.1` → откат на GLX, `Failed to set render target`
при проверке устройства, ALSA seq — безвредны). Сводка `[frames]` одна — за первую минуту после старта
(меню, загрузка мира): p50 = 4 мс (меню рисуется ~250 кадров/с — ограничения нет), 88 интервалов
~180–200 мс — похоже на экран загрузки. Фризы в самой игре по этому журналу не разобрать: следующей
сводки нет, журнал экспортирован раньше.

Сделано:
- игра работает только на быстрых ядрах (`CpuCores`): без самого медленного кластера, если остаётся
  не меньше 4 ядер (8 Gen 2: 3–7 из 0–7), иначе на всех. Сродство процессу игры ставит Winlator при
  появлении окна (`cpuList`/`cpuListWoW64` контейнера). В строке `[launch]` — `cpus=3-7/0-7`;
- строка `[cpu]` раз в минуту (`CpuLoad`, `CpuInfo`): загрузка по потокам приложения, Wine и игры с
  ядрами, на которых их застали (`Gothic2c.exe(main) 97%@7`), средняя частота кластеров, свободная
  память, `thermal` — запас до перегрева (1.0 — начало троттлинга). Читается без root: /proc своего UID
  и cpufreq; что не читается — пропускается;
- сводки `[latency]`, `[frames]`, `[cpu]` пишутся и при уходе с экрана игры или выходе из неё — короткая
  игра перед отправкой журнала в него попадает; `[latency]` теперь за период, а не скользящая.

Как читать `[cpu]`: главный поток Gothic около 100 % — упор в процессор (Box64), помогает меньшая
дальность видимости; поток на ядрах 0–2 — не сработало сродство; высокий `wineserver` — цена
выключенного ESync; частота быстрых ядер сильно ниже наибольшей при `thermal` около 1 — перегрев.

Замечено, но не менялось:
- «Ограничение FPS» в настройках в режимах WineD3D ни на что не влияет (было только для `dxvk.conf`):
  игра рисует без ограничения (`vblank_mode=0`, `mailbox`, Present в X-сервере завершается сразу).
  Ограничитель через X-сервер (задерживать IdleNotify, как `sendIdleNotifyScheduled`) возможен, но
  добавит задержку ввода на глубину очередей WineD3D/glthread/Zink — решать после замеров `[cpu]`.
- ESync выключен — ожидания объектов Windows идут через wineserver (он сам под Box64).
- Winlator `TurnipConfigDialog.setEnvVars`: `sysmem` для Adreno 7xx затирается последней строкой
  (`deck_emu`), на 740 работает режим GMEM. Не трогаем, пока нет признаков упора в GPU.
- Дальность видимости профиля `adreno-7xx` — `sightValue=8` (пресет QUALITY).

### Журнал с `[cpu]`: упор в процессор, D7VK + Turnip по умолчанию (2026-10-14)
Журнал за 6 минут игры (классика, WineD3D + Zink (Turnip), Adreno 740):
- сродство сработало: `cpus=3-7/0-7`, главный поток Gothic на ядре 7 (Cortex-X3);
- в игре **~10 FPS** (интервал кадра p50 = 83–120 мс), главный поток Gothic — **96–98 % ядра**;
  `wined3d_cs` — 28 %, поток Zink (`zfq0`) — 6 %, wineserver — 4–9 %, память ~3 ГБ свободно.

  Box64) не успевает; видеокарта и поток отрисовки простаивают;

### D7VK: падение при запуске — ошибка D7VK 1.11, исправлена одним байтом (2026-10-14)
С режимом D7VK + Turnip игра сразу показывала «Access Violation»: запись по адресу `00000008h` в
`DDRAW.dll`, стек — `D3DXGetDeviceCount` → `CD3dutGlobals::InitializeIfNeeded` → `CHelInfo::Initialize`
(D3DX7, вшитая в Gothic) → `zCRnd_D3D::XD3D_InitPerDX`. Причина найдена в исходниках D7VK 1.11
(`src/ddraw/ddraw7/ddraw7_interface.cpp`): в `GetCaps` в ветке `lpDDHELCaps != nullptr` первая
строка меняет `lpDDDriverCaps->dwCaps2`, а D3DX7 вызывает `GetCaps(NULL, &hel)`. В D7VK 2.x исправлено
(коммит «Add early D3D API support»), но Winlator 11.2 поставляет 1.11.
- Подтверждено по двоичному файлу из архива Winlator (`d7vk-1.11.tzst`): инструкция
  `and dword [ebx+8], 0xFFEFFFFF` по RVA 0x42CB6 — младшие 16 бит совпадают с адресом падения
  (`…3CB6`), в снимке регистров `EBX = 0`; указатель на HEL — в `esi`.
- `BinaryFix` (core): точечное исправление файла по SHA-256 до и после, атомарная запись. Для D7VK —
  байт ModRM 0x63 → 0x66 (`[ebx+8]` → `[esi+8]`), длина та же, релокаций нет. Проверено на настоящем
  файле: меняется один байт, дизассемблер показывает `[esi+0x8]`, повторное применение — «уже исправлен».
- Winlator: новый крючок `onWineSystemFilesReady()` — после распаковки файлов контейнера, до запуска
  Wine. `GameActivity` исправляет там `syswow64/ddraw.dll` (каждый запуск; другие файлы не трогаются).
- Почему прошлый D7VK (Vortek + Gladio) падал иначе: встроенный ddraw Wine (`ddraw_.dll`) с Gladio
  не инициализировался, `GetCaps` прокси возвращал ошибку раньше ошибочной строки, и Gothic падала
  позже — на «maximum texture size». С Zink прокси работает, и выполнение доходило до ошибки D7VK.
- Профиль D7VK для Gothic II привязан к `Gothic2.exe`; для классики (`Gothic2c.exe`) его настройка
  `ddraw.forceLegacyPresent = True` (фон экранов загрузки) задаётся через `DXVK_CONFIG`. Журнал D7VK
  управляется своими `D7VK_LOG_LEVEL`/`D7VK_LOG_PATH` (не `DXVK_*`, которые глушит Winlator): по
  умолчанию info, в вывод Wine, без файлов у игры — его строки видны в журнале диагностики.
- D7VK + Turnip остаётся режимом по умолчанию на Adreno.

### D7VK + Turnip работает: 30 FPS без фризов; артефакты вывода кадра (2026-10-14)
Журнал с исправлением (`d7vk: fixed GetCaps (HEL)`): игра запускается в D7VK + Turnip, настройка для
`Gothic2c.exe` применилась (`Found config env`). Сводки по минутам: **fps=30.0** (упор в ограничитель 30), интервал
кадра p95 = 40 мс, p99 ≈ 43 мс, фризов (>100 мс) — 0–1 в минуту (14 и 18 — в минуты подгрузки новых
мест: потоки компиляции шейдеров `dxvk-shader` до 40 %). Главный поток Gothic — 43–56 % ядра (было 98 %
в WineD3D при 10 FPS), `dxvk-frame` — 25 %, wineserver — 10 %. Через 4 минуты — `thermal status 1`,
частота ядра 7 падает до 2,1–2,5 ГГц, но 30 FPS держатся.

Видео пользователя: целиком белый и целиком чёрный кадр, на снимке — сетка чёрных прямоугольников
≈16×4 пикселя игры (размер блока сжатия UBWC у Adreno) поверх всей картинки. Причина в X-сервере
Winlator (`PresentExtension.presentPixmap` → `Texture.copyFromSource`): кадр игры копируется в
текстуру окна `glCopyImageSubData` в своём контексте EGL, а затем только `glFlush()` — без ожидания.
Сразу после этого экран (другой поток и контекст) может взять недокопированную текстуру, а игра
получает `IdleNotify` и рисует следующий кадр (начиная с очистки) в то же изображение, которое ещё
копируется — на плиточном GPU получается смесь блоков двух кадров или целиком очищенный кадр.
Mesa (Turnip 26.2) перед показом в режиме MAILBOX ждёт конца отрисовки (`x11_needs_wait_for_fences`),
так что со стороны игры кадр готов; гонка — только в X-сервере. При 10 FPS (WineD3D) почти не видна.
- Исправлено в Winlator (`Texture.copyFromSource`): после копии — `glFenceSync` + `glClientWaitSync`
  (до 100 мс, чтобы сбой GPU не остановил X-сервер); IdleNotify уходит после окончания копии.
- Журнал D7VK — `D7VK_LOG_LEVEL=warn`: на info он писал ~5000 строк о 16 устройствах перебора D3DX7.
- Если белые/чёрные кадры останутся — следующий подозреваемый `ddraw.forceLegacyPresent` (кадр из
  теневой основной поверхности после 2D-вывода вне сцены): попробовать без него.

### Белое мерцание при повороте камеры; вылет после установки APK поверх (2026-10-14)
Пользователь: в D7VK игра идёт без лагов и вылетов; чёрное мерцание после исправления гонки в X-сервере
исчезло, **белое осталось** — при нажатии кнопок справа, особенно при повороте камеры (движение мыши).
На белом кадре видео кнопки нашего оверлея нарисованы как обычно — белый именно слой Winlator, со
слабыми контурами (не пустой экран).
- Причина по исходникам D7VK 1.11 (`ddraw7_surface.cpp`): с `ddraw.forceLegacyPresent` у основной
  поверхности есть теневая, и после `Blt`/`BltFast`/`Lock`→`Unlock`/`GetDC`→`ReleaseDC` по основной
  поверхности **вне сцены** D7VK (при `legacyPresentGuard = Auto`) сразу выгружает её и делает
  `Present` — показывает остатки 2D-вывода вместо кадра игры. Профиль D7VK для Arx Fatalis с той же
  настройкой ставит `legacyPresentGuard = Strict` «от мерцания из-за GDI-вывода».
- Сделано: `DXVK_CONFIG = "ddraw.forceLegacyPresent = True; ddraw.legacyPresentGuard = Strict"` для обоих
  вариантов (настройки пользователя DXVK важнее профиля — `Config::merge` не перезаписывает). Возможная
  цена — фон экранов загрузки (ради него профиль и включает forceLegacyPresent); проверить.

Вылет после установки нового APK поверх старого (приходится удалять и импортировать игру заново).
По коду причина не найдена: версия rootfs (23) не меняется, путей к APK в rootfs нет, при старте
нет ничего, что падало бы на старых данных. Найдена слабость: `killWineProcesses` искал процессы Wine
правилом Winlator «потомки или номер больше нашего» — процессы, оставшиеся от прежнего процесса
приложения (например, убитого установкой), с меньшими номерами им не находились. Теперь — все живые
процессы нашего UID, кроме самого приложения (своих процессов у приложения нет).

### Сетка чёрных пятен и белое мерцание остались; Turnip рисовал через GMEM (2026-10-14)
Пользователь (свежая установка, классика): в D7VK + Turnip по-прежнему сетка чёрных чёрточек по всему
кадру (на снимке — правильная решётка, не случайные блоки) и белые вспышки. В WineD3D + Zink (Turnip)
артефактов нет, но `fps=22`, затем `8.6`: интервал кадра p50 = 5 мс, p95 = 188 мс, ~100 фризов в минуту,
главный поток Gothic 86–91 % ядра — упор в процессор, как и раньше. В D7VK — ровные 30 FPS, ~40 % ядра.
- Причина по исходникам Winlator 11.2 (`TurnipConfigDialog.setEnvVars`): для Adreno 7xx (кроме
  710/720/732) задумано `TU_DEBUG=sysmem` (рисование прямо в память, без плиточной памяти GPU), но
  последняя строка записывает `TU_DEBUG` заново из исходного значения — остаётся только `deck_emu`.
  Так Adreno 740 рисовал через GMEM, а у Turnip на a7xx это известный источник сетки чёрных блоков и
  мерцания. Режим WineD3D + Zink идёт через тот же Turnip, но там кадры другие (и в 3 раза реже).
- Сделано: `TU_DEBUG` ставим сами в `GameActivity.onSetupLogging` для режимов с Turnip
  (`GraphicsMode.turnipDebug`: 7xx → `sysmem,deck_emu`, 710/720/732 → `gmem,deck_emu`, иначе `deck_emu`);
  в журнале — строка `[launch] TU_DEBUG=…`. Цена sysmem — больше обращений к памяти; при 1280×720 и
  30 FPS ожидается без потери кадров, проверить по `[frames]`.
- Если сетка останется — следующие подозреваемые: сжатие UBWC (`TU_DEBUG=…,noubwc`) и режим показа
  MAILBOX (`MESA_VK_WSI_PRESENT_MODE=fifo`).

### Чёрные пятна ушли; белое мерцание — только от джойстика камеры (2026-10-14)
Журнал с `TU_DEBUG=sysmem,deck_emu` («Ночь Ворона», 17 минут): ровные 30 FPS, p99 41–45 мс, фризов почти
нет, главный поток 40–70 % ядра — `sysmem` скорости не стоил. Пользователь: чёрных точек и зависаний
нет, **белое мерцание осталось и появляется только при повороте камеры джойстиком камеры**; джойстик
бега и кнопки — без мерцания. Поворот камеры — единственный ввод, который двигает мышь X-сервера
(`injectPointerMoveDelta`); клавиши — нет.
- Что делает движение мыши в X-сервере Winlator: `Pointer.setPosition` → `GLRenderer.onPointerMove` →
  `requestRender()`. Экран Winlator перерисовывается не только по новому кадру игры (после копии кадра в
  `PresentExtension`), но и с частотой касаний — в произвольный момент между кадрами. Курсор при этом
  рисовать нечего: Gothic его прячет (курсор окна с пустой маской, `Cursor.isVisible() = false`).
  Перерисовка между кадрами берёт текстуру окна, которую в это время может переписывать копия
  следующего кадра (другой контекст EGL; блокировка `renderLock` защищает только запись команд, а не
  их выполнение на GPU).
- Сделано (патч Winlator, `GLRenderer.onPointerMove`): перерисовка по движению мыши — только если
  курсор будет виден (тот же выбор курсора, что в `renderCursor`) или его надо стереть (`cursorDrawn`).
- Если мерцание останется — причина не в перерисовке, а в том, что делают с мышью Wine/игра; тогда
  смотреть доставку мыши (`sendRawMotion`, перенос курсора Wine в центр окна).

### Вылет при сохранении в классике: не было каталога `Saves_GII` (2026-10-15)

### Выход из игры: ложный «сбой» и вылет при повторном запуске (2026-10-15)
Пользователь: после выхода из игры следующий запуск пишет, что игра в прошлый раз упала; «Играть снова»
вылетает при загрузке.
- **Ложный сбой.** Сбоем считался любой выход быстрее 3 минут (`QUICK_EXIT_SECONDS`): быстрый проверочный
  выход через меню давал экран «Игра закрылась». Теперь исход определяет `GameExit`: выход через наше меню —
  `USER_QUIT`; процесс игры завершился сам без признаков сбоя — `GAME_QUIT` (выход из меню Gothic); в выводе
  Wine `err:seh:`, «Unhandled exception/page fault» или `symbol_demangle` (обработчик сбоев Gothic) — `CRASHED`;
  окно игры так и не показалось — `NOT_STARTED`. В журнале — `[game] exited after Ns: <исход> (строка сбоя)`.
- **Вылет «Играть снова».** Winlator рассчитан на одну игру на процесс: после игры его `exit()` вызывает
  `AppUtils.restartApplication` (`Runtime.exit(0)`). Мы `exit()` переопределили и оставались в процессе —
  вторая игра запускалась поверх состояния первой (X-сервер, PulseAudio, нативные библиотеки графики,
  статические поля Winlator) и падала при загрузке. Теперь после уборки (процессы Wine, отметка сеанса,
  файлы варианта, копии сохранений) процесс завершается (`GothicApplication.endGameProcess`), если на экране
  нет наших окон. Лаунчер, открытый в процессе, где уже была игра (`gameSessionUsed`), ждёт уборки и
  перезапускает процесс (`restartProcess`); `GameActivity` в таком процессе не стартует.
- После сбоя экран «Игра закрылась» открывается сразу (лаунчер → перезапуск процесса), после штатного
  выхода приложение закрывается, а следующий запуск сразу открывает игру.
- Заодно убрана гонка: отметка сеанса снималась в фоне, и лаунчер, открытый в эти секунды, видел «Игра
  была прервана». Теперь лаунчер в том же процессе всегда ждёт уборки.

### Игра прямо из папки игрока, без копии (2026-10-15)
Пользователь: зачем переносить игру в приложение — нельзя ли запускать из папки, где она лежит?
- Почему было копирование: по плану (раздел 18) — SAF вместо доступа ко всему накопителю. Через SAF
  приложение получает только адреса `content://`, а Wine нужны обычные пути — поэтому копия во внутреннее
  хранилище. Но приложение и так собирается с targetSdk 28 (как Winlator), а при нём обычное разрешение
  «Файлы» (READ/WRITE_EXTERNAL_STORAGE) даёт доступ по путям ко внутренней памяти — так Winlator и запускает
  игры из «Загрузок».
- Сделано: папка по-прежнему выбирается системным выбором (и проверяется по SHA-256); `StoragePaths`
  переводит её в путь (`primary:…` → `/storage/emulated/0/…`, `raw:` из «Загрузок»); кнопка «Играть из
  этой папки» запрашивает разрешение, проверяет папку уже по путям (то же, что увидит Wine), пробует
  записать (`GameFolder.prepare`), создаёт каталоги сохранений и запоминает `settings.gameDir`. Диск D:
  контейнера, `GOTHIC.INI`, раскладка варианта, сохранения и их копии — от `app.gameRoot()`.
- Если игра раньше была скопирована: сохранения из копии переносятся в папку (слоты, которых там нет;
  `current` не переносится), затем предлагается удалить копию (≈2,6 ГБ); если какие-то слоты совпали —
  копия остаётся. Копирование в приложение осталось запасным путём: для карты памяти (писать туда напрямую
  Android не даёт), облака, USB.
- Чем платим: игра пишет в папку игрока (`Gothic.ini`, сохранения, на время классики — переименованные архивы
  аддона, как `Gothic2c.bat`); общая память телефона работает через FUSE — загрузка может быть медленнее,
  проверить. Если папку переместили/удалили или отозвали разрешение — экран выбора папки с объяснением.

### Чёрные линии и белые вспышки вернулись; варианты исправления в настройках (2026-10-15)
Пользователь (классика, D7VK + Turnip, три запуска, самый долгий — 12 минут): «чёрные мерцания в виде
линий, иногда белые блики на весь экран». Журнал: ровные 30 FPS, фризов почти нет, `TU_DEBUG=sysmem,deck_emu`
дошёл до игры (переменные запуска приложения Winlator применяет последними), `d7vk: fixed GetCaps (HEL)`;
в выводе Wine ошибок отрисовки нет (`Unhandled render state 26/136` — DITHERENABLE и CLIPPING, безвредны).
- Путь кадра заново проверен по исходникам. Mesa 25/26 в режиме MAILBOX (Winlator ставит его через
  `MESA_VK_WSI_PRESENT_MODE`) ждёт конца отрисовки до PresentPixmap, буфер снова отдаёт игре только по
  IdleNotify (`COMPLETE` его не освобождает), а IdleNotify после нашего исправления уходит после конца
  копии. Буфер кадра игры — HAL BGRA_8888 без флагов CPU, общий с Turnip только как fd и шаг строки, то есть
  линейный (UBWC в общем буфере нет). Профиль D7VK для `Gothic2.exe` (forceLegacyPresent и maxFrameRate) на
  `Gothic2c.exe` не действует — forceLegacyPresent и Strict ставим сами, как и раньше.
- Найдена одна несинхронизированная пара: экран Winlator (поток GLSurfaceView) рисует из текстуры окна, а
  копия следующего кадра пишет в ту же текстуру из другого контекста EGL. `renderLock` упорядочивает только
  запись команд; выполнение вывода на GPU могло совпасть с копией. Исправлено в патче Winlator:
  `Texture.markScreenRead` (отметка `glFenceSync` после вывода окна, под `renderLock`), `copyFromSource` ждёт
  её (до 100 мс) перед копией. Чёрных пикселей эта гонка сама по себе не даёт (смесь двух соседних кадров),
  поэтому вероятнее, что артефакт рождается в отрисовке игры.
- Увидеть экран нельзя, поэтому — **«Настройки → Изображение → Мерцание: вариант исправления»**
  (`FlickerFix`), каждая догадка — отдельный вариант:
  - «Обычный» — как было (`sysmem`);
  - «1 — без сжатия кадра» — `TU_DEBUG=…,noubwc,nolrz`: ошибки UBWC/LRZ у Turnip на a7xx дают чёрные
    блоки 16×4 и мигающие полосы на геометрии;
  - «2 — точная глубина» — `ddraw.supportD16 = False`: D7VK первым предлагает 16-битный буфер глубины; если
    Gothic берёт его, наложенные и далёкие поверхности мигают линиями при повороте камеры;
  - «3 — всё сразу, строгий режим» — 1 + 2 + `flushall` (сброс кэшей GPU после каждой операции; медленнее).
  В журнале — `[launch] flicker_fix=… DXVK_CONFIG=…` и `TU_DEBUG=…`.
- Как читать ответ: помог 1 — оставить `noubwc,nolrz` по умолчанию для Adreno 7xx; помог 2 — `supportD16 =
  False` по умолчанию (и проверить, что игра стартует); только 3 — синхронизация в Turnip (`flushall` слишком
  дорог, искать точечный флаг); не помог ни один — дело в выводе кадра, нужен снимок/видео: линии
  горизонтальные через весь экран (вывод) или лежат на предметах и двигаются с миром (отрисовка).
- Белые вспышки: если они в дождь/грозу — проверить, не молния ли это самой игры; иначе — следующий
  подозреваемый `InitializeOrUploadD3D9` в `Flip` у D7VK (выгрузка 2D-копии заднего буфера поверх 3D-кадра
  после `Lock`/`GetDC` по нему).

### Журнал пишется всегда и сам, до последней строки перед вылетом (2026-10-16)
Пользователь: после вылета журнал не сохранялся, его приходилось выгружать. Что было не так:
- журнал лежал во внутренней памяти приложения — без «Отправить журнал» его не увидеть;
- строки писались через очередь фонового потока: при падении процесса хвост очереди (последние события
  перед вылетом) пропадал;
- вывод Wine обрезался после 2 МБ («журнал Wine обрезан») — в долгой игре терялся как раз конец;
- падение нашего процесса (драйвер, X-сервер, звук) в журнал не попадало: Android хранит только код
  причины (`ApplicationExitInfo`), трассировка была лишь в logcat.

Сделано:
- `Diagnostics`: каждая строка сразу пишется в открытый файл без буфера (`FileOutputStream` в режиме
  дописывания) — данные в ядре и переживают падение процесса. Очереди больше нет.
- Вывод Wine прокручивается, а не обрезается: `wine.head.log` — первые 2 МБ запуска, `wine.1.log` и
  `wine.log` — последние 2–4 МБ (то, что было перед вылетом). Прошлый запуск — `wine-prev.*`.
- `LogcatCapture`: `logcat -v threadtime -b main,system,crash -f logcat.log` — отдельный процесс пишет
  системный журнал нашего процесса в реальном времени (обратная трассировка нативного падения, исключения
  Java, ANR). При старте он выгружает и буфер прошлого процесса; файл прошлого процесса — `logcat-prev.log`.
  Разрешение не нужно: приложение читает только свои строки.
- `LogLocation`: папка журнала — **«Загрузки/Gothic2Mobile/logs»** (debug: `logs-debug`), видна в любом
  диспетчере файлов. Нужно разрешение «Файлы»: лаунчер спрашивает его **один раз** при первом запуске
  (`logPermissionAsked`). Без него — `Android/data/<пакет>/files/logs` (видно с компьютера), затем
  внутренняя память. Если папка стала недоступна во время игры — запись продолжается во внутренней памяти.
  Когда разрешение дали позже (выбор папки игры, «Настройки → Журнал пишется автоматически»), журналы
  переносятся (`GothicApplication.updateLogLocation`).
- ANR: стеки потоков от Android сохраняются в `anr-trace.txt`. В настройках показан путь к журналу.
- «Отправить/сохранить журнал» работают как раньше и добавляют конец logcat (по 400 КБ).

### Второй телефон: realme C71 (Unisoc T7250, Mali-G57) — слабый процессор, нет Vulkan 1.3 (2026-10-18)

- **WineD3D + Zink:** 2–20 FPS, ~25–45 тысяч строк `GL_INVALID_OPERATION in glVertexAttribDivisor()`
  за игру, однажды `ZINK: vkQueueSubmit failed (VK_ERROR_DEVICE_LOST)`.
- **WineD3D + Gladio («OpenGL — запасной»)** — лучший режим на этом телефоне: местами 20–23 FPS, без потери
  устройства и без потока ошибок OpenGL.
- **Вылет при выходе из игры** (`CRASH_NATIVE`, SIGSEGV в `XConnectorEpoll_destroy`, адрес 0x10): выход из
  меню останавливает среду в потоке интерфейса, от этого завершается процесс игры, и Winlator вызывает
  `exit()` второй раз — из своего потока, одновременно. Оба потока видели `nativePtr != 0` у звукового
  сервера, второй передавал в `destroy` уже обнулённый указатель. Из-за вылета следующий запуск показывал
  «Игра была прервана».
- **Первый запуск:** `System/ddraw.dll.gd3d11 уже существует` — в папке игры были и `ddraw.dll`, и
  `ddraw.dll.gd3d11` без отметки раскладки.

Сделано:
- `GraphicsMode.supportedOn`: режимы Turnip — только на Adreno, D7VK через Vortek — только с Vulkan 1.3
  (`GpuInfo.hasVulkan13`: `FEATURE_VULKAN_HARDWARE_VERSION`). Настройки показывают и «Другая графика»
  перебирает только работающие режимы; сохранённый неработающий режим заменяется режимом по видеокарте.
  На Mali по умолчанию — **WineD3D + Gladio**.
- `GameExit.GRAPHICS_UNSUPPORTED`: строка «No adapters found»/«Failed to initialize DXVK» в выводе Wine →
  экран «Быстрая графика недоступна», режим переключается сам; если система сообщала Vulkan 1.3, а D7VK
  всё равно не нашёл устройство, режим больше не предлагается (`SettingsStore.vulkanFailed`).
- `WINEDEBUG=err+all,fixme-all,err-d3d`: без ошибок d3d WineD3D не создаёт отладочный контекст OpenGL, а
  журнал не забит ошибками Zink.
- Выход из игры: `GameActivity.exit` останавливает среду один раз; в Winlator `XConnectorEpoll.destroy`
  — `synchronized` (патч).
- `VariantLayout`: копия того же файла на месте назначения удаляется, другой файл откладывается под
  `<имя>.old` — запуск больше не останавливается.
- `DevicePerformance`: оценка самого быстрого ядра (ГГц × скорость архитектуры из `/proc/cpuinfo`,
  Cortex-A76 = 1). Ниже 2,0 (Cortex-A76 на 2 ГГц) — перед первой игрой предупреждение «Телефон слабее,
  чем нужно игре». T7250 — 1,55, S23 Ultra — 3,36. Порог уточнять по отзывам.

## 2026-10-21 — Пробная сборка на OpenGothic: сенсорный бой и автобой

7 и 17 октября 2026 у него появился порт на Android (нативно, ARM64 + Vulkan; меню с касанием, игрового
сенсорного управления нет). Без Wine/Box64/D7VK — значит, без нашего мерцания; код движка у нас — бой и

основное не трогаем. Пользователь согласился, главное — бой.

**Что сделано** (патчи `third_party/opengothic.patch`, `opengothic-tempest.patch`; оболочка `og-android/`):
- **Автобой.** NPC в OpenGothic дерутся по таблицам боевого ИИ из скриптов игры (`FightAlgo`, `Fight.dat`);

  ход берётся сам (`fetchInstructions` — у героя нет скрипта `ZS_Attack`), тактика — человеческая по
  владению оружием (`FAI_HUMAN_NORMAL/STRONG/MASTER`, `Npc::fightTactic`). `PlayerControl::tickAutoFight`
  выбирает цель: тот, кто напал на героя (ZS_Attack/ZS_MM_Attack с целью «герой», до 15 м), или
  враждебный зверь ближе 7 м; не перескакивает между врагами; меч достаёт сам, только если на героя
  уже напали; оглушённых людей не добивает (они `isDown`). Палец на джойстике или кнопке боя —
  герой слушается игрока, отпустил — автобой продолжает. Здоровья < 25 % — зелье лечения
  (`ITPO_HEALTH_01..03`, `ADDON_04`, слабые первыми), не чаще раза в 4 с. В журнале — `[g2m] autofight`.
- **Удержание «Удара» = серия.** `Pose::isComboWindow` — та же проверка окна комбо, что в
  `continueCombo`, без побочных эффектов: удар отправляется только в открытое окно (в Gothic удар
  раньше окна обрывает серию). Держать «Удар» — цель зафиксирована, герой доворачивается к ней;
  свайп по «Удару» влево/вправо — боковой удар в ближайшее окно; «Блок» — держать. Добить оглушённого —
  только новым нажатием, удержание никого не убивает. Пока держат «Удар»/«Блок», джойстик не двигает
  героя. Управление на телефоне — всегда Gothic II (`g2Ctrl`), независимо от `useGothic1Controls`.
- **Сенсорный слой** (`TouchInput`, был заготовкой с одним квадратом): плавающий джойстик слева
  (вперёд/назад; вбок — поворот, с оружием — шаг в сторону), обзор пальцем справа (своя чувствительность,

  листать), «Выбрать», «Назад»; касание мимо кнопок там поглощается (тап не применит предмет). Ролик и
  сцена — «Пропустить». Подписи — шрифтом игры (Windows-1251). Кнопка «Назад» телефона — Esc (патч Tempest).
- **Сохранение без клавиатуры**: пустое имя сохранения заменяется датой и временем.
- **Оболочка** (`og-android/`, пакет `gothic2.mobile.og`, «Gothic II · проба»): экран запуска — разрешение

- Сборка: `tools/fetch-opengothic.sh`, `tools/build-opengothic.sh` → `build/og/gothic2-og.apk` (подпись —

### Графика пробы: телефон грелся; «Взять всё» (2026-10-21)

- **Настройки графики — на экране запуска** (`og-android/GraphicsSettings.java` → `files/g2m.ini`, движок читает при

## 2026-10-22 — Отряд защищает от всех; строй, поиск пути, телепорт отставших

  (`ASSESSFIGHTSOUND`), а сам нападал только на тех, кто бьёт героя; горожанин, которого бьёт герой, героя не
  бьёт — значит, «не враг».
- **Почему терялись.** `ZS_Follow_Player` ведёт к герою `AI_GotoNpc`, а в OpenGothic это движение **по прямой**
  к NPC (`go2.set(npc)`, без `wayTo`), — за углом напарник упирается в стену. Далеко от героя NPC
  обрабатываются упрощённо (`AiFar`/`AiFar2`) — он стоит там, где отстал. Все шли к одной точке — к герою — и
  толкались.
- **В пути** (`tickSquadFollow`): след героя — точки через 1,5 м, пока он на земле (64 точки, ~90 м; рывок
  больше 15 м — перенос или другой мир — след заново). Направление хода — по следу (повернулся на месте —
  строй стоит). Места в строю веером позади (углы ±30°, ±75°, ±12° от «прямо за спиной», 2,7–4,4 м); место за
  стеной (луч от героя) — точка на следе, цепочкой. Цель видна — `Npc::goToPos` (новое: идти к точке на земле,
  `GT_Point`; «дошёл» — по горизонтали от ног, иначе центр NPC на 0,9 м выше никогда не «доходил»); не видна —
  к самой свежей видимой точке следа (k-й в строю пропускает k последних — цепочка); нет — `AI_GoToPoint` к
  точке пути у героя (поиск пути по сети, не чаще раза в 4 с). Шаг/бег — с запасом, без дёрганья. Скрипт
  ведёт сам, только если отстал дальше 8 м (`AIV_FollowDist` = 800).
- **Телепорт** (`squadTeleport`): дальше 35 м; 8 с не видит героя дальше 12 м; 6 с не сдвинулся, хотя до
  героя больше 6 м, а до места больше 2,5 м. Куда: точка следа в 3–8 м за спиной героя (своя для каждого);
  следа нет — точка пути в 10 м, которую видно от героя. Пока герой в воздухе, плывёт, на скамье — нет. Не
  чаще раза в 5 с.
- Мелочи: лечение (`tickSquadHeal`) и выход из дела на привале и из позы получают паузу в 1–1,5 с, чтобы ход
  отряда не сбил их.

## 2026-10-22 — Строй теснее, лагерь «Ждать здесь», «Собрать» в обход деревьев

Пользователь: 1,8 м между напарниками — слишком много, нужно около полуметра. «Ждать» иногда сводит всех в
одну точку — нужен лагерь: остаются на местах, кто-то садится, кто-то разговаривает и т. д., никуда не уходят
(разве что сесть на скамейку или стул рядом); танцы и молитвы убрать — несуразно. «Собрать» должен бежать к
вещам по сети путей, а не по прямой, и видеть вещи за деревьями.

- **Строй.** Места: двое в 1,4 м за спиной (±0,55 м вбок), трое в 2,4 м (−1,1/0/+1,1 м), один в 3,4 м — центры
  соседей в 1,1 м, между плечами около полуметра; цепочка по следу — через 1,1 м. Дошёл до места — точнее
  (`Npc::goToPos`: 30 см по горизонтали, «на месте» — 0,5 м); упреждение по ходу героя — 0,3 с.
- **Почему сходились в точку.** «Ждать» ставил распорядок `ZS_Stand_ArmsCrossed` на ближайшую к каждому точку
  пути — у стоящих рядом это одна и та же точка; скрипт ведёт к ней (дальше 5 м) и к свободным точкам
  «STAND». Теперь **лагерь** (`squadCamp`): точка распорядка — метка `G2M_CAMP` (её нет: `Npc_GetDistToWP` —
  максимум, `AI_GotoWP` ничего не находит), цикл распорядка в лагере молчит (`Npc::isCompanionCamp` в
  `implAiTick`, начало состояния выполняется — оно включает перцепции), место запоминается
  (`CompanionIdle::campPos`). По приказу с колеса каждый поворачивается к ближайшему товарищу.
- **Дела в лагере:** сидят (40–90 с, на своём месте; у костра — если он в 8 м), садятся на свободную скамью или
  стул в 8 м (`AI_UseMob`, как `ZS_Sit_Bench`; потом возвращаются на место — когда встанут: цель движения
  раньше очереди не дала бы встать), беседуют стоя, **болтают сидя** с соседом (сидя движок не играет жесты —
  только голос), курят, едят, пьют, лютня, магия. Танцы и молитвы убраны везде; «пописать» — только рядом со
  стоящим героем. Махать мечом — только если никого нет в 2 м.
- **Сон.** `World::setDayTime` (кровать, перевод времени скриптом) вызывает `resetPositionToTA` — движок
  переносит всех NPC к точкам распорядка: идущих за героем уносило к месту найма, ждущих без точки удалял бы
  совсем. Нанятых теперь оставляет на месте (`Npc::resetPositionToTA`).
- **`GT_Point`.** В прошлой версии «дошёл» по горизонтали стало у всех `GT_Point`, в том числе у подхода к
  скамье в `AI_UseMob` — для возвышенных мест там возможна петля. Теперь только для своей точки на земле
  (`GoTo::ground`, после загрузки сохранения — для любой `GT_Point`, `AI_UseMob` всё равно ставит свою заново).
- **«Собрать».** Цель годится, если видна из глаз, **чуть сбоку или сверху** (ствол, куст, забор не заслоняют:
  лучи от глаз ±1 м и на 1,5 м выше) или в 8 м от неё есть точка сети путей, откуда её видно. Дорога: видна
  напрямик — прямо; нет — `AI_GoToPoint` к той точке (поиск пути в обход), потом к вещи. Упёрся на 2,5 с — в
  обход по сети; и там застрял — пропустить. Время на дорогу — 7 с + 0,6 с на метр.

Проверено в облаке: движок с `-Werror`, патч на чистый OpenGothic, тесты, lint, APK. На телефоне не проверено.

## 2026-10-22 — Камера в пути: свободный обзор, ракурсы, «кино»; галочки «Сражаться» и «Собирать лут»

Пользователь: пока герой бежит из точки в точку, камера должна свободно крутиться и не влиять на героя — просто
смотреть. Кнопку, чтобы менять камеру: издалека, с высоты птичьего полёта, сбоку, от первого лица; и как в гонках —
камера сама следит с разных ракурсов, «красивый осмотр». При выборе пути бегом — две галочки «Сражаться» и
«Собирать лут», по умолчанию стоят. Подробно — docs/CONTROLS.md («Камера в пути», макет
docs/images/controls-travel-camera.jpg).

- **Почему раньше нельзя было смотреть.** `MainWindow::tickCamera` каждый кадр ставит поворот камеры по герою
  (`spin.y = pl->rotation()`), а палец (`tickMouse`) поворачивает и камеру, и героя (`player.onRotateMouse`): в
  бою и сборе по дороге (очередь ИИ пуста) герой крутился бы от пальца.
- **«Режиссёр» камеры** (`Camera::setDirector`): откуда и куда смотреть задаёт внешний код; камера сглаживает
  перелёт (5/с), не уходит за стены (`calcCameraColision` от героя к камере, как у обычной), склейка (`cut`) —
  без перелёта; цель для теней — герой. `clearDirector` возвращает обычную камеру: цель — герой (а не место, где
  она была до пути), поворот за спиной; дальше она сама плавно подлетает.
- **Камера пути** (`common/game/travelcamera.*`). Курс — по движению героя, сглаженный (2,5/с), в бою — прежний.
  Палец (`tickMouse` в пути → `TravelCamera::look`) — поворот вокруг героя, на героя не влияет. Ракурсы:
  свободная (3,8 м, 14°), издалека (11 м, 26°), с высоты (24 м, 68°, без столкновений, но над землёй, крышей или
  кроной в своей точке не ниже 4 м — `landRay` сверху), сбоку (5,6 м), от первого лица (кость головы,
  22 см вперёд — как первое лицо движка; без сглаживания), **кино**: планы по долям каждые 6–10 с — погоня низко,
  спереди с покачиванием, сбоку слева/справа, кран с облётом, с высоты с облётом, низкий план снизу вверх и
  **камера у дороги**: точка пути в 20 м впереди, 5 м вбок (сторона — случайно, потом другая), высота глаз над
  землёй, дорогу оттуда видно (луч), не над обрывом; держится, пока герой не пробежит мимо и не отбежит на 7 м
  (не дольше 14 с). Смена плана — склейка.
- **Где включается** (`MainWindow::tickCamera`): путь бегом, не разговор, не сумка, не ролик. Новый путь
  (`PlayerControl::travelSerial`) — курс заново и без поворотов пальцем; после разговора — склейка.
- **Кнопка камеры** (`C_Camera`) — внизу посередине над строкой «В пути» (справа — обзор, слева — джойстик: мимо
  кнопки путь не прервать), значок — текущий ракурс; коснуться — следующий, подержать или потянуть — колесо
  ракурсов (`Wheel::Camera`, выше остальных колёс: не закрывает кнопку). Значки: кинокамера, горы, птицы,
  человек и камера сбоку, глаз, хлопушка; галочки — квадрат с отметкой и пустой.
- **Галочки** на карте «Путь» (`mapFight`, `mapLoot` → `PlayerControl::TravelOptions`): без «Сражаться» враги не
  останавливают героя (бежит дальше, напарники дерутся сами); здоровья меньше четверти — остановиться и выпить
  зелье, зелий нет — стоп. Без «Собирать лут» — без сбора по пути и после боя. Помнятся до выхода из игры. В
  журнале — `[g2m] travel: run to … fight/no-fight loot/no-loot`.

Проверено в облаке: движок с `-Werror`, патч на чистый OpenGothic, тесты и lint оболочки, APK; значки и раскладка
— макетом. На телефоне не проверено: как выглядят ракурсы в настоящем мире (камера у дороги, с высоты над лесом),

## 2026-10-22 — Оптимизация движка под телефон

Пользователь: продумать максимальную оптимизацию движка и игры — всё, что хоть немного помогает; посмотреть
дальность видимости и появления предметов, исправить ошибки прорисовки. Замеров с телефона на OpenGothic пока
нет, поэтому разобран кадр движка целиком (процессор и видеокарта) и сделано всё, что безопасно без проверки
на устройстве; где эффект зависит от телефона — в журнал пишется строка `[perf]`, по ней следующий шаг.

**Что съедало процессор (главная причина нагрева):**
- **Скелеты всех NPC мира каждый кадр.** OpenGothic, в отличие от оригинальной Gothic (она убирает NPC дальше
  50 м), держит в мире всех (в Хоринисе — сотни) и каждый кадр пересчитывал позу каждого (десятки костей),
  а кости заново грузил в видеопамять. Теперь (`Npc::animLodDue`): ближе 40 м от камеры или героя — каждый
  кадр, до 80 м — через кадр, до 160 м — раз в 4, дальше — раз в 8; не на экране (кроме ближних 20 м) —
  вдвое реже; дальше прорисовки — раз в 16. У каждого NPC свой кадр обновления (нагрузка ровная). Время не
  теряется: поза считается по времени мира, звуки и частицы анимации — за весь пропущенный промежуток.
  Решение принимается на главном потоке, пересчитываются только те, кому пора, — рабочие потоки больше не
  будятся каждый кадр ради сотен пустых задач.
- **Ветер двигал все деревья и кусты мира** (тысячи объектов) каждый кадр с перезаливкой их данных. Теперь
  (`VisualObjects::preFrameUpdateWind`): ближе 30 м — каждый кадр, дальше — через кадр, у границы (60 м или
  150 м — настройка «Ветер») качание плавно затухает до покоя, за ней объект не трогается.
- **Точный ограничитель кадров** (`MainWindow::render`): кадры через равные промежутки по часам с
  микросекундами, а не «доспать до 33 мс» с точностью до миллисекунды — ровный темп на дисплее 60/120 Гц.
- **Подсказки планировщику Android (ADPF, Android 13+)** — `common/utils/mobileperf.*`: после каждого кадра
  системе сообщается, сколько процессорного времени он занял из бюджета (1/FPS) — главный и рабочие потоки.
  Система держит частоты ядер не выше нужного (меньше нагрев) и раньше поднимает их перед тяжёлым кадром.
  Функции берутся из `libandroid.so` по имени (на Android 9–12 их нет — просто не используются).
- **Охлаждение:** раз в 10 с читается состояние перегрева (Android 10+); при «сильном» — не больше 30 FPS, пока
  телефон не остынет до «лёгкого». В журнале — `[perf] overheat … / cooled down`.

**Видеокарта:**
- **Дымка у границы прорисовки** (`fog.frag`, `Renderer::drawFog`): раньше земля на дальности прорисовки
  обрывалась (за обрывом — небо). Теперь с 60 % дальности дальнее плавно переходит в цвет неба в этом
  направлении (таблица неба `viewLut`), к 95 % — полностью: обрыва не видно, как туман дальности в оригинале.
- **Трава редеет без линии** (`visibility_pass.comp`): порог отсечения мелочи у каждого объекта свой
  (0,7–1,3 от общего, по номеру объекта — не мерцает): трава вдали становится реже постепенно, а не
  исчезает по кругу.
- **Лежащие предметы — втрое дальше** (`VisualObjects::setCullScale`, `WorldView::addItmView`): травы, оружие,
  добыча отсекаются как объект втрое крупнее — при «Сбалансированно» трава для зелий видна ~100 м вместо ~33 м.
  Их немного, видеокарте это почти ничего не стоит.
- **Тени без мелочи** (`DrawCommands::visibilityPass`): в картах теней мелочь отсекается вдвое ближе (даже при
  «все»): тень травинки в карте теней — пара точек, а рисуется она с проверкой прозрачности текстуры.
- **Небо по направлениям** (`viewLut` и `viewCldLut` 512×256 RGBA32F) — раз в 4 кадра: зависит от высоты
  камеры, солнца и облаков, а не от её поворота. **Туман** на телефоне — таблица 128×72×48 вместо 160×90×64
  (вдвое меньше расчёта каждый кадр, туман — плавный градиент).
- **Свет факелов и костров** дальше прорисовки не обрабатывается (`light.vert`).
- **Анизотропная фильтрация** — до настройки (2x–16x; было всегда максимум видеокарты, 16x): патч Tempest
  `Sampler::setAnisotropyLimit`, задаётся в `game/main.cpp` до создания устройства (сэмплер по умолчанию
  создаётся вместе с ним).
- **Простое растяжение до экрана** (при разрешении 75/50 %): одна билинейная выборка вместо 12 выборок фильтра
  Ланцоша на каждый пиксель экрана — самый «широкий» проход кадра.
- **Шейдеры без отладочной информации** в сборке для Android: SPIR-V втрое меньше (15,8 → 5,5 МБ), APK
  27,3 → 17,1 МБ, быстрее создание шейдеров при запуске.

**Android:**
- Экран игры подстраивает **частоту дисплея** под ограничение кадров: режим с наименьшей кратной частотой не
  ниже 60 Гц (30 FPS → 60 Гц вместо 120 Гц) и `Surface.setFrameRate` (Android 11+) — меньше расход и ровнее кадры.
- Манифест: `appCategory="game"` — система и игровые панели производителей видят в приложении игру.
- **Слабый телефон** (оценка самого быстрого ядра ниже Cortex-A76 на 2 ГГц: `DevicePerformance`, перенесено из
  прежней версии) — при первом запуске сразу «Экономно».

**Настройки графики** (экран запуска, `GraphicsSettings`): новые — «Растяжение до экрана» (простое/чёткое),
«Чёткость текстур вдали» (анизотропия 2x/4x/8x/16x), «Ветер в траве и деревьях» (выключен/рядом/далеко),
«Счётчик кадров на экране» (FPS вверху посередине; в наборы не входит). Наборы: «Экономно» — 50 %, простое
растяжение, 30 FPS, без теней, 250 м, трава рядом, 2x, ветер рядом; «Сбалансированно» — 75 %, чёткое, 30 FPS,
средние тени, 500 м, 4x, ветер рядом; «Красиво» — как у движка на компьютере, ветер далеко. У игрока с прежними
настройками новые параметры берутся из того набора, с которым совпадают его настройки.

**Журнал:** раз в 10 с — `[perf] fps=… frame=…ms max=…ms | logic=… anim=… render=… gpu-wait=… present=… | npc
обновлено/всего wind обновлено/всего | thermal=… headroom=… hints=… cap=…` (время в мс на кадр: логика игры,
скелеты, запись кадра, ожидание видеокарты, вывод). Большое `gpu-wait` — упор в видеокарту (снижать
разрешение/тени), большие `logic`/`anim` — в процессор.

**Чего сознательно не делали:** реже обновлять ИИ и движение дальних NPC (большой шаг движения — сквозь стены),
каскад теней через кадр (карта теней поворачивается вместе с камерой), LTO и `-march` для ядер (выигрыш
небольшой, риск сбоев, которые не проверить без телефона), вывод в уменьшенный буфер экрана с растяжением
дисплеем (касания и интерфейс — переделка Tempest).

Проверено в облаке: движок с `-Werror`, патчи на чистый OpenGothic, тесты оболочки (20), lint, APK. На
телефоне не проверено.

## 2026-10-23 — Живой NPC: «HTTP 403 Forbidden» от Ollama Cloud

Пользователь: «Проверить связь» — «Не вышло: HTTP 403: <!doctype html>… 403 Forbidden». Причина воспроизведена
запросом из облака: Ollama Cloud отдаёт эту HTML-страницу на `User-Agent` с «Dalvik» — его Android
(HttpURLConnection) ставит по умолчанию; с любым другим заголовком тот же запрос проходит (`/v1/models` — 200,
неверный ключ — 401 в JSON). Теперь у всех запросов приложения — к модели, списку моделей и озвучке —
`User-Agent: Gothic2Mobile/1.0` (`LlmClient.open`). Текст ошибки — без HTML и с подсказкой (401 — ключ не
подходит, 403 — доступ запрещён, 404 — нет адреса или модели).

Первая версия исправления была с ошибкой: автозамена попала внутрь самого `LlmClient.open` — он вызывал себя
(переполнение стека → «Список моделей» ронял приложение), а `httpPost` («Проверить связь») остался со старым
заголовком (тот же 403). Модульный тест это поймал, но был ошибочно принят за особенность окружения. Исправлено;
тест снова открывает запрос и проверяет заголовок; код приложения проверен на настоящем Ollama Cloud: список
моделей приходит, неверный ключ — 401. Ошибки фоновых потоков настроек и мозга теперь не роняют приложение
(строка на экране); голос телефона для «Прослушать» создаётся в главном потоке.

## 2026-10-24 — «Путь»: лечение в дороге; сюжет игры через разговор с жителями

Пользователь: в пути бегом герой не лечится, пока здоровье не упадёт совсем, — нужно лечиться, когда здоровья

- Без «Сражаться», когда за героем гонятся, — только зелья и только при четверти здоровья (как прежде). В бою пути
  автобой пьёт зелье при трети здоровья (вне пути — при четверти).
- Нечем лечиться, а здоровья меньше четверти — путь прерывается. Журнал: `[g2m] travel: heal start / heal with … /

  общие темы безымянных жителей, как в начале `ZS_Talk`; `storyExec` — тот же `exec`, что у выбора реплики, но

  и не закрывают диалог. `AiNpc::cmdStory` — команда `act story{topic}`: тема или вариант, итог — дневник, вещи,
  золото, опыт, умения, гильдия, новые варианты и темы (`act_done.story`); житель помечен `AIV_TalkedToPlayer`.
- Приложение: инструмент `story_topic` у живых жителей (`Tools.resident`), раздел «Темы разговора» и итог темы —
  `Story`, правила — `Persona.story` (сначала тема, потом пересказ своими словами без потери сути; не выдумывать
  заданий вне тем; выбор — по ясным словам героя). Слова модели до вызова темы отбрасываются, после темы — шаг на

### Ожидается от пользователя

## 2026-10-24 — Меню игры под палец; бессмертные NPC теряют сознание, а не неуязвимы

жизни уходят у всех; бессмертного можно побить до потери сознания, обокрасть, он отлежится и встанет, но убить его

**Меню** (docs/CONTROLS.md, «Меню игры, журнал, сохранения, герой»):
- Меню Gothic было единственным экраном без сенсорного слоя: `TouchMode::Hidden`, касание шло прямо в `GameMenu`
  (касание по строке сразу выбирало). Строки там 13–30 dp высотой: ячейки сохранений — 13 dp, строки журнала — по
  высоте шрифта. Теперь `TouchMode::Menu`/`Ui::Menu`: сенсорный слой лежит **поверх** меню (`MainWindow::setupUi`),
  рисует стрелки, «Выбрать» с подписью действия и «Назад» и отдаёт меню касания мимо кнопок (`e.ignore()`).
- `GameMenu` (телефон): ближайший пункт под пальцем (строка с соседом по `IT_EFFECTS_NEXT` — одна цель), палец ведёт
  подсветку, над пальцем — лупа с выделенным (и значением переключателя), касание выделенного — выбор. Ползунок —
  пальцем вбок относительно, переключатель — шагами по 40.
- **Журнал**: список заданий и запись были вложенными окнами (`Dialog::exec`) — окно забирает все касания, кнопкам
  слоя не досталось бы ничего, а по касанию открывалось выделенное (первое) задание. Теперь это состояния меню
  (`logList`, `logView`, `MenuRoot::back` → `GameMenu::closeSubView`): касание по заданию — выделить, ещё раз —
  открыть; список (`freeScroll`, `Item::more`) и запись листаются пальцем.
- Сохранение без окна ввода имени (на телефоне оно ждало касания): имя — дата и время. Пункт «Управление» в
  настройках скрыт (назначение клавиш ждёт нажатия клавиши), пункты под ним поднимаются.
- Ролик поверх меню («Заставка») — «Пропустить»: `touchMode` смотрит на ролик раньше меню.

**Бессмертные NPC** (`Npc::isKnockoutOnly`):
- В оригинальном движке и в OpenGothic у NPC с `NPC_FLAG_IMMORTAL` урон просто не вычитается (`changeAttribute`).
  Таких в скриптах около девяноста — сюжетные люди (Ватрас, Пирокар, Ли, Гаронд, стража ворот, Сатурас…) и драконы.
- Теперь у бессмертного **человека** (не героя) жизни уходят как у всех, а там, где он погиб бы, — теряет сознание
  (`onNoHealth`: смерть → `ZS_Unconscious`), как нанятый напарник: от кулаков, меча, стрелы, заклинания, от монстра,
  от врага, которому положено убивать. Добить нельзя (`canFinish` — и герою, и NPC через `AI_FinishingMove`); уже
  лежащий от огня и т. п. остаётся без сознания; в воде держится на 1 здоровья (в `ZS_Unconscious` вода — сразу
  `ZS_Dead`). Отлежавшись (`HAI_TIME_UNCONSCIOUS`), встаёт — скрипт `ZS_Unconscious` сам ведёт всё как при обычной
  победе над человеком: «побеждён героем», опыт за первую победу, обыск, реплика при вставании.
- Бессмертные **звери** (драконы до разговора, Разбитый голем) — как в оригинале: урон не проходит (без сознания
  они быть не могут, а по сюжету их нельзя ранить до нужной сцены). Сюжетные смерти (`B_KillNpc`, `B_RemoveNpc`)
  снимают флаг перед ударом — работают как прежде. Заклинания-контроль (сон, смерч, уменьшение) на бессмертных
  не действуют — так решают скрипты игры (`C_CanNpcCollideWithSpell`), это не урон.
- Журнал: `[g2m] immortal "Имя" knocked out by Имя`.

### Ожидается от пользователя

  позвать другого — `talk_to_npc`; у жителя — «просьба поговорить с другим — не тема». Описание `talk_to_npc` — то же,
  и «подойдёшь сам, go_to_npc не нужен».
- `talk_to_npc` к `hero` — обычная реплика (`Tools.heroLine`); `talk_to_npc` другому — слова, при них жест и взгляд

- Слушающий отвечает делом: инструменты `Tools.listener()`, его снимок обстановки, правила `Persona.reactions`;
  действия — после слов, итог — говорящему. Журнал ИИ: `npc <житель> to <говорящий>: «…» действия`.

### Ожидается от пользователя

## 2026-10-25 — Жест — не удар: житель больше не «пляшет» вместо драки

## 2026-10-25 — Драки людей снова до потери сознания, а не насмерть

Пользователь: герой убил Рауля в драке насмерть, жители иногда убивают героя, люди между собой тоже — а должны
сначала падать без сознания. Журнал: перед дракой модель Рауля вызвала `set_attitude hostile` (так же раньше —
Ксардас, Герольд, наёмник). Инструмент ставил **постоянное** `ATT_HOSTILE`, а у человека оно в движке значит бой
насмерть, в обе стороны:
- `Npc::checkHealth`: упавший до нуля умирает, а не теряет сознание, если его отношение к противнику — «враждебно»
  (`personAttitude`; для героя берётся отношение жителя к нему) — так Рауль умер от удара героя, а герой — от
  удара «враждебного» жителя;
- `attackReason` — `AR_GuildEnemy`: добивание лежащего (`B_FinishingMove`), маг — огненный шар вместо оглушения;
- такой житель — «враг» (`PERC_ASSESSENEMY`), нападает сам, а после убийства свидетели мстят герою насмерть
  (`AR_HumanMurderedHuman`) — в журнале после Рауля на героя пошли Гуннар и наёмник.

Скрипты игры ставят человеку постоянное `ATT_HOSTILE` только перед `AR_KILL` (`B_Attack`); обиженный после драки —
временное «враждебно» (`Npc_SetTempAttitude`). Теперь так же: `set_attitude hostile` — постоянное «сердито» и
временное «враждебно» (`AiNpc::cmdAct`); в обстановке модель видит «враждебно». Драка с таким жителем — до потери
сознания (`AR_GuardStopsFight`, как у «сердито»). Старые сохранения: при загрузке постоянная вражда человека к
герою (не враг по гильдии и не `AR_KILL`) переводится в злость (`AiNpc::calmHostility`, строка
`[g2m] ai: "…" hostile -> angry` в журнале). Описание `set_attitude` для модели: «драка с человеком — до потери
сознания, не насмерть».

Не менялось (как в оригинале): бандиты и другие враги по гильдии, звери — насмерть; стрела и боевое заклинание
по человеку убивают; «Добить» — новое нажатие главной кнопки по оглушённому (удержание не добивает).

### Ожидается от пользователя
- Обругать жителя до `set_attitude hostile` и подраться: он падает без сознания, герой — тоже (не умирает).
- Загрузить сохранение с «враждебным» Ксардасом/Герольдом/наёмником: в журнале `hostile -> angry`, драка — до
  потери сознания.
